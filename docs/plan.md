# План разработки: локальный переводчик EN→RU

Ишью: https://github.com/oshliaer/local-line-translator/issues/1. Хэндов (риски): `docs/handoff.md`.

## Коды исполнителей
- **PH** — DeepSeek Pro (High)
- **PL** — DeepSeek Pro (Low/Light)
- **FH** — DeepSeek Flash (High)
- **FL** — DeepSeek Flash (Low/Light)

## Распределение задач по агентам (исполнители)

Принцип: **PH** — только высокая неопределённость/эксперимент и финальный gate; **PL** — сложная, но специфицированная реализация; **FH** — аккуратное исполнение и краевые случаи с низким риском; **FL** — boilerplate без принятия решений.

| Фаза | Задача | Исполнитель | Обоснование |
|---|---|---|---|
| 0a | Установка CPU-torch + модель, замер ОЗУ/задержки | FH | Исполнение + чтение метрик, решений не требует |
| 0b | Выживаемость плейсхолдеров + поведение модели на краевых случаях | **PH** | Риск №1, экспериментальная итерация, цена ошибки максимальна |
| 1 | Каркас: CLI, обход, `_ru`-именование, кодировки, загрузка модели | PL | Фундамент; спецификация ясна, нужна надёжность |
| 2 | Конвейер: FSM кода, защита/восстановление inline-элементов, перевод | PL | Самый тонкий код; специфицирован в handoff |
| 3 | Валидация: Blind+Diff, diff-лог, логи `[VALIDATION ...]` | PL | Ядро экономии токенов; логика ясна (при дефиците бюджета — FH) |
| 4 | Устойчивость: атомарная запись, CRLF/LF, длинные строки, не-UTF-8, exit-коды | FH | Чёткие краевые случаи, объём, низкий риск |
| 5a | requirements + README + фикстуры | FL | Boilerplate |
| 5b | smoke-тест + интеграционная проверка парсинга логов | FH | Прогон + проверка, низкий риск |
| — | Финальное ревью диффа + сквозной запуск CLI (Lead) | **PH** | Gate качества перед сдачей |

## Хэндов-дисциплина (обязательно между сессиями)
Каждая фаза запускается отдельной сессией, поэтому контекст передаётся через файлы:
- **Старт сессии:** читать `HANDOFF.md` (текущее состояние) → `docs/plan.md` (что делать) → `docs/handoff.md` (риски).
- **Конец фазы:** обновить `HANDOFF.md` (статус, решения, факты, как возобновить) и закоммитить. Без свежего хэндофа фазу не считать завершённой.
- **Что фиксировать в `HANDOFF.md`:** закреплённые версии (0a), формат плейсхолдера и fallback (0b), метрики ОЗУ/задержки, отклонения от плана, открытые вопросы.

## Фаза 0 — Spike (разведка рисков) — обязательна до кода — *0a: FH, 0b: PH*
- [FH] CPU-only torch + transformers + sentencepiece; зафиксировать версии (заморозить в requirements).
- [FH] Скачать `Helsinki-NLP/opus-mt-en-ru`; замерить пиковое ОЗУ и задержку на строку.
- [PH] Проверить выживаемость нескольких форматов плейсхолдеров в MarianMT; выбрать устойчивый.
- [PH] Проверить поведение модели на: блоке кода, HTML-теге, ссылке, пустой строке, строке с `\n`.
- Выход: подтверждённый формат плейсхолдера + бюджет ресурсов + fallback-стратегия.

## Фаза 1 — Каркас — *PL*
- [ ] Разбивка на модули и CLI (`--file`/`--dir`).
- [ ] Обход файлов, именование `_ru`, пропуск существующих `_ru`, обработка кодировок.
- [ ] Ленивая загрузка модели один раз на первый перевод; `device='cpu'`, seed, num_threads.

## Фаза 2 — Конвейер строки — *PL*
- [ ] Конечный автомат блоков кода; пропуск пустых/спецсимвольных строк.
- [ ] Защита inline-элементов (ссылки → inline-код → HTML) и восстановление плейсхолдеров.
- [ ] Перевод строки; пост-обработка (стрип `\n`, возврат маркеров).

## Фаза 3 — Валидация — *PL*
- [ ] Blind: сверка числа строк + возврат всех маркеров (count и полное множество).
- [ ] Diff-Error: детектор аномалий, запись diff-лога, отчёт `[VALIDATION WARNING]`.
- [ ] Логи `[VALIDATION SUCCESS]` / `[VALIDATION WARNING]` / `[ERROR]` / `[SKIP]` / `[INFO]`.

## Фаза 4 — Устойчивость — *FH*
- [ ] Атомарная запись, CRLF/LF, отсутствие завершающего `\n`, длинные строки.
- [ ] Не-UTF-8, симлинки, скрытые каталоги, ложные `_ru`.
- [ ] Exit-коды и контракт stdout для Harness.

## Фаза 5 — Упаковка — *5a: FL, 5b: FH*
- [FL] `requirements.txt` (CPU torch) + README (установка, запуск, кэш модели, offline).
- [FL] Фикстуры: `.md` с кодом/ссылками/HTML, CRLF, пустой файл, файл без завершающего переноса.
- [FH] Smoke-тест + интеграционная проверка: запуск через CLI и парсинг логов агентом.

## Финальное ревью (Lead) — *PH*
- [ ] Ревью итогового диффа, сквозной запуск CLI, проверка контракта stdout.

## Предлагаемая структура файлов
```
local-line-translator/
  HANDOFF.md         # живой хэндов между сессиями (читать первым)
  main.py            # вход: CLI, оркестрация
  translator.py      # модель: load + translate_line (cpu, seed, threads)
  inline_protect.py  # извлечение/восстановление плейсхолдеров
  validator.py       # blind + diff-валидация, diff-лог
  fileio.py          # обход, _ru-именование, атомарная запись, кодировка
  requirements.txt
  README.md
  docs/              # issue.md, handoff.md, plan.md
  tests/fixtures/
```
