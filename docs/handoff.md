## Подводные камни (риски) и как их обойти

### 1. Модель и зависимости
- **«300 МБ» — это только веса модели.** torch (CPU) + transformers + sentencepiece добавляют ещё ~1+ ГБ на диск и заметное ОЗУ. Ставить CPU-only wheel (`pip install torch --index-url https://download.pytorch.org/whl/cpu`) и замерить реальный пик ОЗУ.
- **Первый запуск требует сеть** (скачивание весов и SentencePiece `.spm`). Для offline — предзагрузить кэш или `HF_HUB_OFFLINE=1`.
- **MarianMT — это не LLM, он не «сохраняет плейсхолдеры» по инструкции.** SentencePiece может расщепить и исказить `__INLINE_CODE_0__`. Это риск №1 (см. п.4).
- Зафиксировать детерминизм и лимиты: `device='cpu'`, `torch.manual_seed(0)`, `torch.set_num_threads(...)`.

### 2. Построчная целостность
- **Модель переводит по предложениям, а не по строкам** → потеря контекста между строками, качество ниже. Это осознанный компромисс требования «строка-в-строку».
- **Выход модели может содержать `\n`** → ломает счётчик строк. Обязательно стрипать/заменять перевод строки в результате.
- **Непустая строка может перевестись в пусто/пробелы** → это аномалия (diff-warning), но не для строк, состоящих только из символов/пробелов.
- **Переносы строк:** `read().split('\n')` vs `splitlines()`; CRLF vs LF; файл без завершающего `\n`. Нужно гарантировать ровно N строк на выходе и не терять/не добавлять завершающий перенос.
- **Непереводимые строки** (shell-команды, пути, ключи конфигов, числа, URL) модель портит. Стоит добавить эвристику пропуска (низкая доля букв / отсутствие гласных).

### 3. Конечный автомат блоков кода
- **Забор ≠ только ```.** Бывает ```python (info-string), `~~~~`, 4+ бэктиков, вложенные заборы. Правило: строка-забор = первые непробельные символы образуют ` ``` ` (закрывающий — тот же признак).
- **``` на одной строке с кодом** (` ```code``` `) неоднозначен — договориться о правиле заранее.
- **Несбалансированный забор** (открыт и не закрыт) уведёт остаток файла в «код» — логировать warning.
- **Сбрасывать `in_code_block=False` для каждого нового файла.**

### 4. Плейсхолдеры (риск №1)
- **Коллизия:** `__INLINE_CODE_0__` может встретиться в исходном тексте. Использовать уникальный префикс (uuid/случайный) и экранировать реальные совпадения.
- **Модель может потерять/переставить/удвоить плейсхолдер.** Проверять не только `count`, но и полное множество токенов (каждый маркер должен вернуться дословно).
- **Формат плейсхолдера критичен.** Выбирать маркеры, которые MarianMT склонен копировать как один редкий токен (одиночный нечастый символ/токен), и **прототипировать выживаемость до написания основного кода**.
- **Fallback:** если маркер не вернулся — повтор с другим форматом, либо копия исходной строки + запись в diff-лог (агенту — точечно).
- **Порядок извлечения:** сначала ссылки → затем inline-код → затем HTML, иначе вложенные паттерны конфликтуют.
- **Inline-код с двойными бэктиками** (`` `a `b` c` ``) и **URL со скобками** (Wikipedia) не покрываются наивными регэкспами — документировать ограничения.
- **HTML-теги:** не путать `<` `>` в тексте/сравнениях с тегами; матчить по имени тега, а не по любым угловым скобкам.
- **Ссылки:** переводится только `[...]`, URL `(...)` защищается; после перевода проверить, что скобки `[]()` не пострадали.

### 5. Валидация
- **Blind-проверка должна быть дешёвой** (только строки, без повторного вызова модели).
- **Diff-лог выравнивается по индексу строки;** при расхождении числа строк — предусмотреть fallback (иначе пары оригинал→перевод сломаются).
- **«Пустая строка при непустом оригинале» не должна шуметь** на строках из одних символов (это норма).

### 6. CLI и файлы
- **`--dir`:** пропускать `_ru`-файлы, скрытые каталоги (`.git`), всё кроме `.md`/`.txt`, и не ходить по симлинкам.
- **Проверка «уже содержит `_ru`»:** `bar_rus.md` ложно содержит подстроку `_ru`. Использовать `stem.endswith('_ru')`, а не `'_ru' in name`.
- **Кодировка:** не-UTF-8 файл → `UnicodeDecodeError`. Обрабатывать (skip + warning или `errors=`), не ронять весь прогон.
- **Атомарная запись** (temp + `os.replace`), чтобы обрыв не оставлял битый `_ru`-файл, который потом «пропустят».
- **Длинные строки** (>512 токенов Marian) → обрезка/разбиение или явный warning, иначе модель обрежет молча.
- **Exit-коды:** 0 — успех; ненулевой — фатально. Явно определить код для «успех, но есть warning» (чтобы агент мог ветвиться).
- **Баланс логирования:** «подробно» ≠ «логировать каждую строку» — иначе dump лога съест те самые токены агента, которые мы экономим. Логировать: сводку по файлу, `[VALIDATION ...]`, diff-строки, ошибки.

## Контракт stdout для агента Harness
- `[VALIDATION SUCCESS] ...` — файл корректен, агент **не** читает файл (экономия токенов).
- `[VALIDATION WARNING] ...` — точечный список проблемных строк, агент правит только их.
- `[ERROR] ...` — фатальная ошибка (файл/кодировка/модель), агент действует по коду возврата.
- `[SKIP] ...`, `[INFO] ...` — служебные сообщения (пропуск `_ru`, старт/финиш файла).
